# web

The Next.js frontend: the Tactical Console and the Operations Deck. See `/docs/architecture/ARCHITECTURE.md` at the repository root for the full system design.

## Run it

```
cp .env.example .env.local
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000) with `apps/sim` already running. The page connects to `apps/sim`'s `/ws` and renders the Tactical Console live: every node and edge in the real station graph, coloured by type and status, updating as the backend ticks and as faults fire and fixes commit. A status line shows connection state, the current tick, and the last agent-protocol message received.

The Console (`components/console/Console.tsx`) is PixiJS plus pixi-viewport (ADR-0001), promoted from the disposable `prototypes/console-render` prototype once its pan/zoom was confirmed in a real browser (#77). It builds its scene once and updates node/edge graphics in place on every snapshot, rather than rebuilding, so panning and zooming survive a tick. A degraded or critical node pulses a `pixi-filters` GlowFilter in its alarm colour (#50); a nominal node never does. All three edge types animate a hand-rolled dashed flow (PixiJS v8 has no built-in dash support), each with its own colour and dash pattern so they're distinguishable without a legend (#52, #53), speed proportional to the edge's `currentFlow`; a severed edge never animates, that value is static, not live. A stage-level `pixi-filters` CRTFilter (#55) gives the whole console scanlines and a subtle vignette, tuned against the console's own dark background rather than shipped on its generic defaults, applied in screen space so it stays fixed regardless of how the viewport pans or zooms. A hand-rolled alternative using `@blockstacking/jims-shaders` was evaluated and measured objectively worse out of the box (#56), so the stock filter stayed.

Injecting a fault also triggers a short, decaying flicker burst (#57), distinct from the sustained CRT effect: a screen-space white overlay whose alpha follows a deterministic decaying sine (`|sin(progress * 5 * π)| * (1 - progress) * 0.55` over 260ms), redrawn only while active. The same fault also pans and zooms the camera onto its affected node(s) (#63), a deliberate 700ms glide via pixi-viewport's `animate()`; a single node sits at a fixed comfortable zoom, two or more compute their own scale from the bounding box of their positions. Both effects fire on a `fault_alert` agent-protocol message, not the telemetry snapshot: a fault that resolves within the same `/faults` request never appears in any broadcast snapshot (the backend clears a resolved fault from `active_faults` before that request's one snapshot), but `fault_alert` is always broadcast first, before any fix is even attempted, so it's the only signal that fires reliably regardless of how quickly ORION resolves it. It's also never replayed to a reconnecting client, so unlike an earlier snapshot-diffing approach this needs no "already active on first sync" guard.

The Operations Deck (`components/ops-deck/OpsDeck.tsx`, #58) is a crew-manifest strip beside the console: one row per agent, its task text taken from that agent's most recent `status_broadcast`, a brief glow on any new message from it (a 1.8s hold, the backend's whole response trace for one fault arrives in milliseconds, a real-time-only indicator would be imperceptible). Accent colours are drawn from Console.tsx's own node/edge palette rather than a new one, ATHENA's is the exception: no fixed accent, her card colour reflects her actual last verdict, pass green or the same alarm-red Console.tsx uses for a critical node. Each row's ID slot holds a small schematic glyph (`components/ops-deck/avatars.tsx`, #60): a targeting reticle for ORION, a thermometer for VULCAN, a bolt for TESLA, a routed three-node path for MERCURY (one leg using the same dash pattern #52/#53 already use for network_link edges), a gated shield for ATHENA. All `currentColor`, inheriting whatever lit/dim/pulseOverride colour the card itself is already showing, no colour logic of their own.

The mission log (`components/ops-deck/MissionLog.tsx`, #59) turns every agent-protocol message into one readable line (proposal ids, verdicts, reasons, not a generic "message received"), newest at the bottom, auto-scrolled there as entries arrive. Colour reuses the same vocabulary as the rest of the page: fault severity colours, and the pass/fail green/red ATHENA's card already uses for a verdict.

ATHENA's card also has its own distinct checking pulse (#65): a `validation_request` holds a near-white `animate-pulse` state for 1.1s, separate from the generic active glow every other card uses and from her own eventual pass/fail colour, so the validation step itself reads as a moment, not just whatever it resolves to.

MERCURY's card flashes the same alarm-red for 600ms when ATHENA rejects one of her proposals (#66), she's the only agent that proposes a fix today, so any failing `validation_result` is necessarily hers. `AgentCard`'s checking-only prop was generalised into `pulseOverride` for this, both states are the same underlying mechanism (a prioritised, pulsing colour held for a fixed duration) with different colours and durations, owned by `OpsDeck`.

A fault also plays a synthesised alarm klaxon (`lib/audio/useAlarmKlaxon.ts`, #61): a Web Audio API two-tone sawtooth wail, no shipped audio file. It fires on `fault_alert`, which (unlike the flicker burst's fault ids) is never replayed to a reconnecting client, so it needs no "already active" guard. The mute toggle next to the station title persists its state in `localStorage`, per-viewer.

The cockpit HUD (`components/CockpitHud.tsx`, #62), bottom right, is three gauges in one bordered strip rather than separate cards: an odometer-style tick counter, an active-fault count coloured by the worst active severity, and a segmented health bar derived from live node statuses, not the fault list, a rollback still shows as degraded even though its own fault stays active. Depended on a backend fix (#62): `active_faults` was append-only, nothing ever cleared it once ORION resolved a fault, an "active fault count" would only ever have grown.

The Operations Deck chrome (everything except the Tactical Console itself) has a dark/light theme toggle (`lib/theme/useTheme.ts`, #67): `globals.css`'s `--chrome-*` custom properties, scoped via a `data-theme` attribute on a wrapper around the overlay chrome, the Console is a separate sibling of that wrapper and never sees it. Only neutral panel backgrounds, borders, and structural text flip, semantic colours (agent identity, severity, pass/fail) stay the same in both themes, they carry meaning, not just a light/dark preference. Persisted via `localStorage` with a lazy `useState` initialiser from the start, #61's mute toggle needed a live-found fix to land on that pattern, no reason to repeat the race here.

A bottom-centre scrub bar (`components/ReplayControl.tsx`, `lib/replay/`, #68) lets an incident be rewound and re-watched: `useIncidentRecorder` keeps a rolling history of `{snapshot, messages}` pairs, recording on a new message or a new tick, not only a new snapshot, the backend applies a fix atomically so there's only ever one snapshot before a fault and one after, a snapshot-only recording would scrub as a flat before/after with nothing in between. In practice a whole fault's messages usually land in the same React commit (the backend resolves and broadcasts the full trace in milliseconds), so this yields a handful of genuinely distinct steps per incident (quiet, fault detected, resolved), not one step per message, found live verifying it. Scrubbing feeds the frozen historical snapshot/messages to the Console, Operations Deck, mission log, and HUD, which recreates whatever they'd have shown live, including the flicker burst and camera auto-focus firing again as you scrub past a `fault_alert`. The alarm klaxon stays tied to the live stream specifically, re-triggering it by scrubbing past an old fault would be a surprising side effect of navigating history.
